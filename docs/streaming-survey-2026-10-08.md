## 0. The one-paragraph state of play

Cortex today ships whole-resident. A BSP project cooks zero room chunks and a header-only WORLD.PAK (`docs/legacy-grid-boundary.md` section 0). The PXBSP map and its textures are `include_bytes!`'d into the EXE (`generated/level_manifest.cooked.rs:172 PXBSP_WORLD`; `bsp_runtime.rs:939-944` panics with "streamed BSP textures are not implemented"). The only things Cortex streams from CD are (a) the persistent model/animation pack read once on the loading screen, (b) UI images, (c) the sky/cube panorama, (d) UI SFX to SPU. A real room/page streamer exists (`RoomStreamScheduler`, `StreamedRoomPages`, `WorldRoomSlotsReadJob`), but it serves the retired grid world only, and its CD transport is the old DMA path that the console proved unreliable. The P6 design for BSP streaming is written down (`docs/p6-pxbsp-streaming-followup.md`, `docs/bsp-engine-overhaul.md:84-107`) and the format seams are reserved (PXBSP `StreamingIndex` lump, `ReadAt`), but nothing is implemented. The most mature streaming code in the ecosystem is in hk-psx (IRQ-driven CD transport, predictive prefetch, LRU RAM slots, relocatable code modules, SPU ring fed from CD). It is game-local.

## 2. Cortex today

### How a level loads
All at once, in this order (`main.rs:922-1080` `step_streaming_jobs`, `initial_world_ready`):
1. Boot: PXBSP map, BSP textures, cube/sky data, fonts are already in the EXE image (`.data`), because `bsp_runtime.rs:939-944` requires baked texture bytes and `PXBSP_WORLD` is a `'static` slice.
2. Loading scene: `PersistentAssetStreamer::begin(UI_PACK_START_LBA, UI_PACK_TOC, ASSETS)` then `pump` every tick (not just background ticks, because a loading screen has nothing to stay responsive for; `main.rs:926-933`, `model_rendering.rs:494-499`). Models, atlases and animation clips come in from UI.PAK; `load_runtime_models()` parses them; atlases upload to VRAM.
3. `BspRuntime::refresh_materials` binds every BSP material to a VRAM slot (`bsp_runtime.rs:920-980`). `initial_world_ready` (`main.rs:~985`) waits for models loaded and `materials_ready`.
4. For BSP worlds `step_streaming_jobs` then only steps VRAM uploads and material refresh (`main.rs:944-952`). No room stream, no window job. The WORLD.PAK is header-only.

### What is resident (BSP project)
- Whole PXBSP file (91 KB in the current generated tree: `generated/brush_world.pxbsp`, souls slice measured 30,912 B BSP + 3,408 B light + 97,576 B textures in the 08-12 handoff, `quake-psoxide-convergence-handoff.md:1436-1440`).
- All session-resident animation clips: `PERSISTENT_ASSET_PAGE_COUNT = 314` pages = 643,072 B in the current generated manifest (`level_manifest.cooked.rs:150`). Cook ceiling is 481 pages = 985,088 B (`budget.rs:106`, link-measured 491 on 2026-08-31, cap set 10 below).
- All code (`.text` 712,032 B on 0.4b), UI SFX samples in `.data` (56,704 B in July, may have moved since: `ram-vram-survey-2026-07-25.md` item 2; the cooker now has an `ui_sfx` stream path, so unconfirmed which is active).

### Measured headroom and what bounds the level today
- Memory is tight but not the first wall. Frame time is: model `render ~= 734k + 1,856 cycles x visible faces` with player + 2 enemies; 30 fps holds about 150 visible faces, 20 fps about 420 (`engine-stress-limits-2026-10-03.md`, superseded in places by the 10-06 continuation: 29.62 fps at 136 faces with 4096-unit patches + 400% texel scale; 26.23 fps sealed outdoor courtyard).
- That means a streamed world is bounded per VIEW by faces, not by total geometry. Streaming buys world SIZE (many regions, not all resident), not a bigger per-frame view.
- Far-vista texture/flags cook disabled for BSP (`engine-stress-limits` "Far-vista settings currently produce no BSP workload"), so no distant scenery exists to stream yet.
- Emulator limit study (memory only, `limit-study-headroom-2026-09-24`): CD in gameplay costs <= noise CPU; main-RAM stalls are the Cortex ceiling.

### Gaps that already bite
- Polled streaming loses sectors in the emulator when pumped once per frame (sector every 6.7 ms vs 16.7 ms frame). 36 sectors were lost on the Cortex pack until both boot reads were set to `wait_for_sectors`; in-play room streaming deliberately does not wait; floor of 1 lost sector remains; fix is IRQ-driven servicing (memory `psoxide-emu-no-cdda-seek`). The code comment at `cd_stream.rs:1-10` and `WorldRoomSlotsReadJob::set_wait_for_sectors` (`:~420`) match.
- Pump budget: 8 sectors per background tick (`runtime_schedule.rs:26`) on every other sim tick = 240 sectors/s ceiling against a 150 sectors/s drive. Asserted `>= drive_sectors_per_background_tick() = 5` (`cd_stream.rs:79`).
- Seek break-even constant `SEEK_BREAK_EVEN_SECTORS = 8` (`cd_stream.rs:70`) is derived from 4 single-speed sector periods, an old emulator figure. Silicon measured 11 / 79 / 137 / 310 ms for 1 / 16 / 128 / 512 sectors (below), i.e. a 16-sector hop already costs ~12 sector periods at 2x. The constant looks stale against console data. Flagging, not changing.

## 3. Hardware constraints already measured

1. Drive rate. Console 13.20 ms/sector single, 6.49 ms/sector double, within 1% of spec (`docs/emulator-accuracy-from-silicon.md`, "CD-ROM read" section; that section also says PSoXide was 4x slow on 07-26, later calibrated per memory `cd-timing-calibrated-from-silicon`, 780ccd1f). Derived by me: 150 sectors/s x 2048 B = 307,200 B/s at 2x; a 30-sector (60 KB) region is ~200 ms of transfer plus seek.
2. Seek. 11 / 79 / 137 / 310 ms for 1 / 16 / 128 / 512 sectors, NOT monotonic-smooth; timing.rs encodes 12/85/148/335 ms after probe overhead (`emu/.../cdrom/timing.rs:109-143`). Run-to-run silicon swing ~2x, rotational phase dominates (v1.7 capture, `docs/hardware-refs/px7-silicon-2026-07-31-v1.7-full.txt`; memory says do not recalibrate to a single run). Streaming-read cadence still ~12% fast in-emu (memory).
3. CD DMA unreliable on Manny's console. Chopping-burst ch3 DMA either leaves the buffer untouched or latches CHCR busy forever; PIO pops are byte-perfect; the stuck kick poisons later transfers on that channel; rule: `dma::abort` before arming, never an unbounded wait (memory `console-cd-dma-unreliable`; SDK `psx-pack/src/cd.rs:280-294` comment; commit a6f96596a). PIO costs ~1.3 ms/sector more than a working DMA (SDK comment). Derived: continuous 2x streaming would burn ~195 ms of CPU per second on PIO (150 x 1.3 ms), i.e. ~20% of the frame budget. Treat as an estimate to measure.
4. Implicit-seek streams corrupt on console. Bare SetLoc+ReadN started data flowing while the mechanism was still settling; the BIOS brackets reads as SetLoc/SeekL/SetMode/ReadN/Pause and that loads 1.4 MB EXEs cleanly (`psx-pack/src/cd.rs:~560-575` doc of `start_read_seek_first`, traced 2026-08-01). The engine's `hw.rs:76 start_cd_read_at_lba` is the bare SetLoc+ReadN form.
5. CD-DA contention. Silicon: a data read with CD-DA playing (`0x9B`) takes the same time as with audio stopped (`0x9C`): 1647 vs 1657 hblanks (`emulator-accuracy-from-silicon.md` "CD-DA contention"; `hardware-test-disc.md:777-790`). Memory adds: contention wedges drive state AFTERWARDS (STOP+respin), not read speed; fixed in suite v1.7 with PAUSE. DuckStation and PSoXide agree: ReadN while CD-DA plays gives INT3+INT1, no INT5 (memory `cdda-read-contention-verdict`, 2026-06-08). **What none of this measures: whether the music keeps playing while data is read.** The probes time the read only. The SDK XA doc and hk-psx MUSIC.md state the opposite assumption: a read of any other sector stops XA and "restarting it seeks back"; the engine's GameApp comment says one laser cannot read and play at once. Treat "data read interrupts CD-DA/XA audio" as the working assumption, unverified by ear/capture on this console.
6. XA looping and speed change. Looping seeks back (gap = seek time; "not measured yet" on console, `XA-MUSIC.md`). Changing drive speed when music starts costs a moment.
7. Stop/spin-up. Motor down reports status 0x00 for 1 to 2 s after Stop; reads right after Stop failed on console. Emulator spin-down/up is instant (memory `psoxide-emu-no-cdda-seek`, "Still-unmodelled gap"). Matters for any "pause music, burst-read, resume" scheme.
8. Wedged-hardware discipline. Never write bare `while is_busy {}` on DMA or GPUSTAT waits; `PSOXIDE_WEDGE_DMA` / `PSOXIDE_WEDGE_GPU` env vars let the emulator wedge on purpose (memory). The new present queue adds a GPU access guard (recent SDK commits ef37b344a, 942bc0267); any new streaming upload path that touches GP0/VRAM must go through it.
9. hk-psx field evidence on streaming itself: earlier region-streaming builds produced "real late-destination movement holds" (646 boundary-wait ticks in one recorded run, max 90 ticks) and were replaced by whole-scene admission at gates (`hk-psx/docs/STREAMING.md`, "Validation status and earlier streaming work"). Predictive gate prefetch and code/art streaming were reintroduced in hk-finish (handoff `:18`). Whether it now meets "no pop-in" on console is unconfirmed.
10. Main RAM has no data cache; RAM loads dominate frames (limit study, memory). Streamed data must not be re-read per frame from slot memory if avoidable (the render-in-place design of streamed rooms, `level-residency.md`, trades against this).

## 4. Reuse assessment

### Candidates for the shared streaming core
1. **Pack format and cooker plumbing**: `psx-iso` `build_world_pack`, `psx-pack` parser, FNV verification, optional HLZC in-place LZ4 (`psx-pack/src/lib.rs:185`). Keep. Add a "region group" ordering notion (hk-psx `disc.rs` "payloads sit on the disc in the order they are read").
2. **Residency policy**: `RoomStreamScheduler` (pin window, LRU, retry backoff, protected prefix so prefetch never evicts, `room_streaming.rs:270-322`) and `StreamedRoomPages` (page pool with run validation, stale-slot detection, generation counters). The policy is generic, the name is room-specific. Rename/generalise to "region" rather than writing a new one. hk-psx `room_residency.rs` is a small second implementation of the same idea (5 slots, LRU, `wanted`, `loading`, `decode_ready`); compare before choosing.
3. **Transport**: the best transport today is hk-psx `cd_stream.rs` (IRQ-driven, PIO, chained VBlank handler, one sector per interrupt). It does not exist in the SDK; cs-psx has a copy. It should move to the SDK (`psx-io/src/cd/`) as an IRQ-driven reader and replace `psx-game-runtime/cd_stream/hw.rs` (DMA). This is the single highest-leverage shared piece because both emulator sector loss and console DMA risk point at it.
4. **Prefetch policy**: hk-psx `preload.rs` (motion-aware plan, `with_demand`) and `disc.rs` `prefetch_hint/prefetch_take` are the only working predictive prefetch. The p6 doc asks for PVS-row-driven prefetch; none exists. The grid `room_graph_ring` (`room_streaming.rs:1541`) is portal-hop based, not PVS-based.
5. **VRAM**: `VramRuntime` 64-slot allocator + upload queue is reusable as the destination for streamed BSP textures. It was built for grid room tpages (6 tpages, stride 64).
6. **Scheduler vocabulary**: `psx-engine/src/scheduler.rs` already defines `TaskLane::StreamingBudget`, referenced nowhere else (grep). The streamer could register against it.
7. **Music coexistence primitives**: hk-psx SPU ring (`audio_stream.rs`, FIFO + IRQ-address boundary refill) is the only answer that lets music play during loads. hl-psx's suspend/capture-resume-position (`main.rs:4530`) is the cheap answer for CD-DA. Neither is in the SDK.

### Game-specific, do not lift as-is
- hk-psx scene arena/VRAM bank layout, gate blackout flow, and code-module relocation (it depends on a python cooker and link-time import tables). The relocating code pool is the right idea for "enemy code per region" but is tied to hk's linker/hazard tooling (`modules.rs` header; `host/code_modules.py`).
- Grid-specific parts of editor-playtest (`active_rooms.rs`, room window, portal visibility, `room_cache`), now dead behind `USES_PXBSP`.
- hl-psx viewmodel stream (weapon-switch chunk), quake `ChunkStream`.

### Gaps (nothing exists)
- **BSP regions in the cooker**: `StreamingIndex` is written empty. No leaf-cluster to region map, no per-region face/vertex/marksurface payload split, no chunk table with texture dependencies (p6 work item 1). Cook ingredients exist: leaves, portals (`brush_portal.rs`), PVS rows (`brush_vis.rs`, Draft vs Release flow). Resident core (nodes, planes, leaves, clipnodes, PVS, entities, strings) is specified to stay resident.
- **Collision per region**: hull data currently comes from the resident clip nodes (`PXBSP_BODY_HULLS` is a static in the manifest, `level_manifest.cooked.rs:179`). The p6 design keeps collision resident. If worlds outgrow that, collision paging is undesigned.
- **BSP texture streaming**: runtime requires baked bytes (`bsp_runtime.rs:939`). Needs per-region texture packs with refcounts (p6 section 4 "Shared textures are separate"), VRAM slot eviction by region, and a fix for the earlier measured symptom "28 room-material texture drops and 128 upload-queue-full" (`ram-vram-survey` section VRAM; whether still true on BSP unconfirmed).
- **Animation residency**: all clips are session-resident (`budget.rs:96-100` says "When per-scene residency lands this becomes a per-scene figure"). `PersistentAssetStorage::compact()` exists but is never called, and parsed `Model<'static>` views would dangle on relocation (audit "Hazard for the wiring"). Per-region enemy sets need either released clips (generation-checked rebuild) or a fixed set.
- **Enemy/boss code per region**: only hk has it; Cortex code is linked in (712 KB `.text`).
- **Audio coexistence**: no mechanism lets Cortex's CD-DA combat music survive a region read. Current policy is "level fully resident, so no read collides". Options on record: stop/resume CD-DA around reads (hl-psx), SPU ring fed from a RAM FIFO (hk-psx), XA with data interleaved into filler slots (not implemented in encoder/player). Combat music cue is a random start in the first 15 s, so resume-position is not currently tracked (it IS in hl-psx).
- **Miss policy**: skip-and-pop (`visible_missing_mask`, 5.6% misses on the recorded grid route, audit finding 6) versus Manny's HK stance "we cannot accept pop-in" (memory `hk-psx-seamless-ethos`, 10-01). Not decided for Cortex.
- **Prefetch driven by PVS + motion**: unimplemented (p6 items 4, 5).
- **Telemetry**: counters exist (CD_ROOM_CHUNK_LOADS, SIM_PUMP stages, `ROOM_STREAM_FAILED_LOADS`); p6 item 7 asks for per-chunk latency, hit/miss, eviction counts.
- **Editor support for defining regions**: none. NodeKind list has no region/streaming-volume node (grep of `scene_types.rs`, `streaming.rs` is only resource-use collection). The old grid way was "Portal markers in the Room node" (audit section 10). A BSP equivalent would be auto-clustering from portals/PVS with an authored override, plus a budget report in the editor (the grid audit noted `over_budget_count()` was not surfaced while authoring).
- **Tests for the CD layer**: `cd_stream.rs`/`hw.rs` have no unit tests and the emulator is "ideal hardware" for them. The wedge env vars cover DMA/GPU only. A pageable BSP reader behind `ReadAt` is testable on host with `SliceReader`.
- **Console validation**: every doc (p6 item 9, HK STREAMING.md) says paging is a CD-latency question and the console run is mandatory.

### Smells to surface (not touched)
- Three independent copies of an IRQ-driven CD transport idea (hk-psx `cd_stream.rs`, cs-psx `cd_irq.rs`) plus the DMA-based engine `hw.rs`, plus oot/alttp loaders still on DMA. Violates "shared improvements live in the shared engine".
- `psx-pack/src/cd.rs:294` has a function named `dma_read_sector` that is PIO. Misleading name.
- `cd_stream.rs` doc and `SEEK_BREAK_EVEN_SECTORS` use pre-silicon figures.
- `hk-psx/docs/STREAMING.md` is partly stale and has text-joining typos ("contains106"), and contradicts the later hk-finish prefetch work.
- `PersistentAssetStorage::compact` and several grid paths are dead but kept "for later" (`#[allow(dead_code)]`).
- Docs disagree on the data-vs-music model: the contention probe says no penalty, the GameApp and HK/SDK docs say one laser.
