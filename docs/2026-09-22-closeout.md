# 2026-09-22 source closeout

The second consolidation pass and the Celeste emulator audio investigation are
banked as separate changes. This is a source and validation handoff, not a claim
that every game uses one renderer or runs at 60 FPS.

## Shared runtime ownership

- [psx-goldsrc](../engine/crates/psx-goldsrc/README.md) owns the HSFX voice/bank
  runtime, cached CD chunk sessions, clipping/projection with explicit view
  policies, texture-animation updates, sparse model-variant lookup and cold PVS
  face compilation used by both HL and CS. The ports keep authored IDs, their
  existing cache capacities, visibility unions and gameplay policies. Frozen
  legacy code is confined to test oracles, not a second production runtime.
- [psx-chainloader](../engine/crates/psx-chainloader/README.md) owns the demo disc
  and Arcade executable transport, checksum/retry checks and machine handoff.
  Each collection supplies its loading presentation. Existing malformed-header
  preconditions remain documented; extraction is not additional media hardening.
- SDK primitives remain owned by PSoXide, emulator behavior by PSoXide-emulator,
  and these engine crates by PSoXide-editor. Imported component files are pinned
  build inputs, not independently maintained source copies.

The consolidated editor baseline is `a834cd870f5b79626b74ae0b9d8541ad2f027d8a`.
The corresponding completed port heads are HL `62fad1c9`, CS `52ea646d` and
Quake `499bd3d3`. Quake's change closes the editor pin and guarded build
provenance; it does not introduce a new renderer. DS, ALttP and OoT were excluded
from the harmonisation scope.

Validation included frozen old-behavior oracles, real MIPS builds and hazard
checks, exact state/packet contracts, and multi-frame gameplay. CS exercised
horizontal and vertical split views and restoration of the full view. HL routes
covered the tram, chapter loading and weapon use. Quake exercised movement,
firing and menu-selected E1M1/E1M2 loads; that is not a natural episode-completion
claim. Decoupled presentation can change intermediate screenshots even where
simulation and ordered render inputs agree; those differences were investigated
rather than called pixel parity.

## Emulator and frontend audio

[Emulator revision 0d6e8bf8](https://github.com/EBonura/PSoXide-emulator/commit/0d6e8bf8b263c5304026e164d220b8f2801f7e59)
contains two independently validated corrections:

1. GPU DMA retries no longer query an environment variable intended only for
   MDEC tracing. A sampled replay showed materially lower host execution cost
   with identical guest state, audio and final image. This is host headroom,
   not an increase in emulated guest FPS.
2. The SPU advances on the emulated clock before observable accesses, so elapsed
   samples cannot be changed retroactively by later register writes and due
   audio IRQs are visible without waiting for a frontend pump. The owning
   [SPU clock document](https://github.com/EBonura/PSoXide-emulator/blob/0d6e8bf8b263c5304026e164d220b8f2801f7e59/docs/spu-clock.md)
   describes that contract and its regressions.

The editor follows that revision in `010dfff7`. Both frontend variants drain
already-produced audio rather than treating a zero catch-up count as an empty
queue. A real CLI regression runs a synthetic loop executable and checks that
its WAV contains every elapsed sample. The previous caller produced an empty
WAV in that case. Normal debug/release editor builds pass, and the recorded
Celeste route matches the accepted standalone build across all 48 software
captures, full RAM, SPU RAM, route log and complete PCM output. No audio buffer
size, game logic or guest assets were changed for these fixes.

## Burn and remaining limits

The prepared HL-inclusive image is labelled `v0.38-10-g2a93225-HL`. Its preburn
checks covered all launcher entries, deeper gameplay routes, audio-track layout
and hazard classification. Subsequent user feedback reports the Celeste collection
working on the console. That report is not a timed hardware performance result.

Celeste 2's observed post-hookshot 30 Hz guest presentation remains a separate
cadence investigation; these changes do not claim to resolve it or establish a
hardware/emulator timing match. The emulator has reproducible audio-clock and
host-cost fixes, but final listening through the user's GUI audio device is
still a user check. The existing burned image was not rewritten or reburned by
this investigation.
